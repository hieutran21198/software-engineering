# Change-owned delivery requirements

## Need and scope

R1. Future versions contain complete requirements, specifications, and applicable decisions. Tasks and their plan remain only in the originating change. New changes start from version knowledge and create a fresh plan, without inherited task copies.
R2. Keep completed change tasks, dependency metadata, DoD results, and evidence available for long-term delivery traceability. A new change must not overwrite a delivered change's plan. Required delivery sources must remain resolvable through version provenance.
R3. Preserve established snapshots, existing outcome membership, and all referenced legacy evidence. The policy applies to new versions; do not migrate or remove delivered snapshots.
R4. Unit completion must use evidence associated with the delivered member, with protected-ref publication and existing all-required-merges obligations. Modified, missing, ambiguous, or branch-only task evidence must not prove historical completion.
R5. Update the canonical reusable bundle and its packaged delivery consistently, including role instructions, foundation/model, lifecycle, task format, unit evidence, examples, and adoption guidance. Keep unrelated bundle content and required skills intact.

## Acceptance examples

A new version has no tasks directory and identifies its source change. Its retained change exposes the executed plan and checks. The next change has a fresh plan. Existing version-task evidence remains readable. A branch edit to a delivered change's checks cannot establish that evidence.

## Impact and self-check

ADD owns retention and evidence contracts. Artifact Plane consumes them through the existing artifact dependency. No new artifact edge or state store is needed. User scope is explicit; KISS keeps one task authority and STE preserves evidence and establishment limits. No Requirement blocker remains.
