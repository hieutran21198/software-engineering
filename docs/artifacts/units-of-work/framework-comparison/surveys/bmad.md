BMad keeps you in control while its agents and workflows make the important decisions explicit and preserve them as context" (`README.md` › Why BMad?). Its tagline is "turn an idea or change request into working software without giving up the thinking".

## 2. Workflow

The overall model is one delivery loop: Clarify → Plan → Build and verify → Learn and adjust. Larger work "enters it earlier and goes round it more often" (`docs/index.md`; `docs/images/bmad-delivery-loop.svg`).

**Phases and skills** (`docs/plan/choose-a-planning-path.md`, `docs/reference/skills-and-agents.md`):

1. **Getting to a defined intent** (optional, any order, "independent tools, not stages"): `bmad-brainstorming`, `bmad-forge-idea`, `bmad-deep-recon`, `bmad-product-brief`, `bmad-prfaq`, `bmad-prd`, `bmad-ux`, `bmad-architecture`.
2. **Requirements and slicing:** Sofia (`bmad-agent-po`) runs SPEC, slice (initiative → epics), refine (epic), incept (epic → ordered stories), validate, board, replan and store setup (`skills/bmad-agent-po/workflow.md` › Dispatch/Intake).
3. **Implementation**, one session per unit: `bmad-build` (attended) or `bmad-build-auto` (unattended worker, one ticket per call).
   - Build steps: `step-01-clarify-and-route.md` → `step-02-plan.md` → `step-03-implement.md` → `step-04-review.md` → `step-05-present.md`, or `step-oneshot.md` (`skills/bmad-build/`).
4. **Review and testing:** `bmad-code-review` (standalone), `bmad-walkthrough` (guided human review), `bmad-qa-generate-e2e-tests`.
5. **Close:** `bmad-retrospective` per epic, then Sofia closes the epic (`docs/build/finish-an-epic.md`).

**Commands:**
- Skills are invoked by name, e.g. `/bmad-build 2.3`.
- Agent menu codes also work, e.g. Amelia `BD`, Sofia `SPEC`/`TICKETS`/`REFINE`/`BOARD`/`VALIDATE`/`REPLAN`/`STORE` (`docs/reference/skills-and-agents.md` › Agents).
- The `bmad` hub skill recommends the next step and runs `bmad setup`, `bmad status` and `bmad migrate method`.

**Mandatory steps:**
- No planning phase is mandatory. "You don't need BMad for an obvious, low-risk edit" (`docs/plan/choose-a-planning-path.md`). A story "needs no refining before `bmad-build`" (`docs/plan/set-up-the-ticket-tree.md`).
- Inside Build, the step sequence is enforced: "NEVER skip steps or optimize the sequence" (`skills/bmad-build/workflow.md`).

**Approval gates and who approves:**
- **Build CHECKPOINT 1** (full route): the human approves the plan ("Approve and continue / Approve and stop / Review plan"). The `<frozen-after-approval>` block is then locked: "only the human can change it" (`skills/bmad-build/step-02-plan.md`). Open Questions must be answered before the checkpoint.
- **Build halts** on a dirty tree or a branch mismatch, on a multi-goal intent (split/keep), and when the plan exceeds 1600 tokens (split/keep) (`skills/bmad-build/step-01-clarify-and-route.md`, `step-02-plan.md`).
- **Ticket status:** Build stops at `built`. "Only you, or an orchestrator, mark a story done" (`docs/plan/set-up-the-ticket-tree.md`; `tools/ticket-tree-rules.md` › Status).
- **Organisational sign-off moments** (`docs/plan/plan-inside-an-organization.md` › Where Sign-Off Happens):
  1. PRFAQ verdict
  2. PRD validate
  3. Architecture spine review
  4. Ticket-breakdown approval
  5. Retrospective verdict
- **Sofia:** "A yes approves what was shown and, on the repo store, is the yes to commit it" (`skills/bmad-agent-po/workflow.md` › Conventions).
- **Unattended runs:** entry flags `plan_checkpoint` and `done_checkpoint` are for the orchestrator to honour (`docs/build/autonomous-development-loops.md`).

## 3. Artifact model

**Artifact types** (`docs/plan/choose-a-planning-path.md` › Planning Skills and What They Produce):

| Artifact | File(s) |
|---|---|
| Brainstorm | `brainstorm.html` + `brainstorm-<topic>.md` |
| Forge | `forge-report.html` + `forge-<slug>.md` |
| Research | `research-<topic>.md` |
| Brief | `brief-<slug>.md` + `addendum.md` |
| PRFAQ | `prfaq-<slug>.md` |
| PRD | `prd-<slug>.md` + `addendum.md` + `.memlog.md` |
| UX | `DESIGN.md` + `EXPERIENCE.md` + `ux-<slug>.md` |
| Architecture spine | `architecture-<slug>.md` |
| Tickets | initiative / epic / story / spike / bug files, `tickets.toml` |
| Build plan | `story-<slug>-plan.md` or `plan-<slug>.md` |
| Other | `deferred-work.md`, `epic-<slug>-retrospective.md`, ADRs `adr-<slug>.md` (`skills/bmad-deep-recon/references/codebase.md`) |

**Layout:**
- Each document is `<type>-<slug>/<type>-<slug>.md` inside `{output_folder}/{active_initiative}/` (default `_bmad-output`).
- Each container keeps its breakdown in `tickets/` with `tickets.toml`; standalone tickets go in `backlog/` (`docs/plan/set-up-the-ticket-tree.md` › Create an Initiative Store; `skills/bmad-agent-po/workflow.md` › The ticket tree).
- A parent initiative can list child initiatives.

**Format:**
- Markdown with YAML front matter. The ticket template carries `id`, `type`, `parent`, `covers`, `sources`, `companions`, `after`, `refined`, `hitl`, `risk` (`skills/bmad-agent-po/assets/ticket-template.md`).
- The breakdown is TOML `[[entry]]` / `[[epic]]` / `[[initiative]]` tables, where table order is build order (`skills/bmad-agent-po/assets/tickets-template.toml`).
- The plan front matter holds `status`, `ticket`, `baseline_revision`, `route`, `risk`, `review`, `lenses_ran`, `review_loop_iteration`, `context` (`skills/bmad-build/plan-template.md`).
- IDs:
  - PRD: `FR-n`, `UJ-n`, `SM-n` (`skills/bmad-prd/assets/prd-template.md`).
  - Spine: `AD-n` (`skills/bmad-architecture/assets/spine-template.md`).
  - Ticket requirements: `R<n>`.
  - Entries: numeric or alphanumeric `id`; refs are `epic.entry`, e.g. `2.3`.

**Source of truth:**
- The ticket at each altitude "is the spec", and its Requirements section is what Build reads. "When the PRD and a ticket's Requirements disagree, the ticket's Requirements win and the PRD is a source" (`docs/plan/define-requirements-and-a-specification.md`; `docs/plan/plan-inside-an-organization.md`).
- Requirements and Constraints are *derived* from an append-only `.memlog.md`. Sofia is the only writer, and hand edits are overwritten (`skills/bmad-agent-po/references/spec.md` › Memory and derivation).
- The PRD is "the document the organization owns". Edits go there and later skills are re-run (`docs/plan/plan-inside-an-organization.md`).
- Once a leaf story file exists, it is truth over its entry (`docs/plan/set-up-the-ticket-tree.md`).
- For brownfield code, the code is truth. Project context stores only what code cannot say (`docs/existing-codebases/theory-of-project-context.md`).

**Versioning over time:**
- Planning documents are living and updated in place: PRD Update mode; Sofia re-derives with "ids kept"; the spine is "kept current" (`docs/plan/design-ux-and-architecture.md`).
- Per-change records are the build plans. They are kept after completion as "live ticket state" and evidence (`skills/bmod-method/help/artifact-lifetime.md`).
- There are no version numbers or snapshots on specs. History comes from Git; the docs recommend the output folder be its own git repo (`docs/plan/set-up-the-ticket-tree.md`).

## 4. Change on existing systems

**How a change is expressed:**
- A small change is a free-text intent to `bmad-build`, which writes a plan with Intent, Boundaries (Always/Never), an I/O & Edge-Case Matrix, a Code Map and Tasks (`skills/bmad-build/plan-template.md`).
- Larger changes become a new initiative or epic whose requirements Sofia writes.
- There is no delta-spec format against a baseline spec: absent (checked: `docs/`, `skills/bmad-agent-po/references/`, `skills/bmad-build/`).

**Mid-flight change:**
- Sofia's REPLAN names the change, re-runs SPEC with ids kept, "nam[es] entries whose `covers` cite a changed id", re-slices the affected epics, drops obsolete entries, and records a dated `Decision:` line. There is "No proposal file … nothing already built is rewritten" (`skills/bmad-agent-po/references/replan.md`; `docs/plan/break-work-into-stories-and-track-it.md` › Replan).
- In an organisation: PRD Update → Sofia → spine update → re-slice (`docs/plan/plan-inside-an-organization.md` › When Requirements Change Mid-Flight).

**Archival and merge of completed changes:**
- Plans are kept, not archived: "Deleting one removes the state and evidence later builds, review, and retrospective read" (`docs/plan/break-work-into-stories-and-track-it.md`).
- Superseded planning documents "can be archived once their references and requirement sources remain accessible" (`skills/bmod-method/help/artifact-lifetime.md`).
- The retrospective proposes "spec reconciliations … for you to apply to the project contract by hand" (`docs/build/finish-an-epic.md`).
- There is no automatic merge of a delivered change into a living system spec: absent (checked: `docs/build/finish-an-epic.md`, `skills/bmad-retrospective/workflow.md`).

**How current truth is kept:**
- Code plus the `AGENTS.md` block, maintained by `bmad-project-context` refresh/record/audit (`docs/existing-codebases/set-and-maintain-project-context.md`).
- Living PRD, spine and ticket requirements.

## 5. Traceability

**Chain:**
- PRD `FR-n` (realizes `UJ-n`; `SM-n` "Validates FR-x").
- → initiative `R<n> (FR-2, FR-5)`.
- → epic `R<n> (parent R<m>)`; the epic's `covers`.
- → story entry `covers = ["R1"]` plus a `verify` line.
- → plan (`ticket:` joins the plan to the entry; Given/When/Then ACs; `baseline_revision`).
- → commits `baseline_revision..<next baseline_revision>`.
- → `## Code Review` blocks and the retrospective.

Sources: `skills/bmad-prd/assets/prd-template.md`; `skills/bmad-agent-po/assets/ticket-template.md`; `skills/bmad-agent-po/assets/tickets-template.toml`; `tools/ticket-tree-rules.md` › The plan file / Baseline; `docs/build/autonomous-development-loops.md` › Orchestrator Responsibilities.

**Architecture link:** spine decisions `AD-n` have `Binds: {R ids}`, plus a "Capability → Architecture Map" (`skills/bmad-architecture/assets/spine-template.md`).

**Validation:** Sofia's validation checks that "Tickets cover every Requirements line", that "each `covers` id exists", and that "every source id on a Requirements line exists in a `sources:` file" (`skills/bmad-agent-po/references/validate-checks.md` › Set/Tree).

**Code → reason:**
- There are no in-code annotations, by design. The dev agent principle says "Never add epic or story references as inline code comments" (`skills/bmad-agent-dev/customize.toml`; `CHANGELOG.md` v6.11.0 Fixes #2544).
- The reverse path runs from commit ranges via plan `baseline_revision`, and via ADRs proposed by `bmad-deep-recon` from git history or by the retrospective (`skills/bmad-deep-recon/references/codebase.md`; `skills/bmad-retrospective/workflow.md`).
- Open issue #3063: "a plan's baseline_revision does not survive a squash merge" (https://github.com/bmad-code-org/BMAD-METHOD/issues).

**Tests:**
- Matrix test audit: every I/O-matrix row needs a test that ran and passed (`skills/bmad-build/step-03-implement.md`).
- A test → requirement ID scheme is absent (checked: plan template, `bmad-qa-generate-e2e-tests`). The TEA module's `bmad-testarch-trace` is external (`docs/build/test-completed-work.md`).

## 6. Impact analysis

**What it detects:**
- **Requirement-ID change:** an update that changes or retires an `R` id must "name the stale entries and the tickets whose `covers` cite it" and offer a re-slice (`skills/bmad-agent-po/references/spec.md` › When lines change).
- **Source drift:** "a source changed since the memlog last cited it, is read against the memlog and the other sources; each disagreement … is put to the user" (`spec.md` › The Operation).
- **PRD Update** "surfac[es] conflicts with earlier decisions before applying anything" (`docs/plan/define-requirements-and-a-specification.md`).
- **`tickets.py status`** structural checks: `drift` (leaf vs entry `after`/`hitl`), `unpinned_after`, `undeclared_after`, `order_conflict`, cycles, orphan plans (`skills/bmad-agent-po/scripts/tickets.py` docstring; `references/board.md`). This is deterministic code with tests (`scripts/tests/test_tickets.py`).
- **Code-claim staleness:** Build re-checks codebase-research claims "when … its cited file changed since that commit (`git diff --stat <commit> -- <path>`)" (`skills/bmad-build/step-02-plan.md`).
- **Project-context refresh** "diffs deletions and renames since the recorded commit" (`docs/existing-codebases/set-and-maintain-project-context.md`).
- **Source conflict:** source vs code produces a `Source conflict:` note (`docs/plan/set-up-the-ticket-tree.md`).

**What it lacks:**
- An automated dependency graph from requirements to code, or detection of code changes that invalidate a spec: absent (checked: `docs/`, `skills/bmad-agent-po`, `skills/bmad-build`, `tools/`).
- Propagation is LLM-driven inside Sofia's runs, except for the structural checks in `tickets.py`.
- Trackers do not sync automatically: "Hooks are not integrated yet, so nothing syncs on its own" (`docs/plan/set-up-the-ticket-tree.md`).

**Handoff format:**
- The plan file is "the contract between planning, implementation, and review". The implementer receives only the plan path: "the plan is the subagent's sole source of truth" (`step-03-implement.md`).
- Build Auto exposes a terminal `status`, `blocked_reason`, `deferred:` list, `followup_review_recommended` and `## Auto Run Result` (`docs/build/autonomous-development-loops.md`).

## 8. Quality controls

**Build plan gates:**
- READY FOR DEVELOPMENT standard: actionable, logical, testable (Given/When/Then), complete, sufficient, coherent.
- SCOPE STANDARD: single goal, 900–1600 tokens.

Sources: `skills/bmad-build/workflow.md`; `step-02-plan.md` (self-review).

**Review and triage:**
- Lenses: quick (one reviewer, the Build default) or thorough (several lenses, the `bmad-code-review` default).
- Triage verifies each finding, grades it `high`/`medium`/`low`/`false`/`maybe-false`, and logs every finding in `## Review Triage Log`.
- Routing: `intent_gap` (revert, ask the human), `bad_plan` (revert, amend the plan, re-implement), `patch`, `defer` (to `deferred-work.md`).
- The loop limit is 5 iterations.

Sources: `skills/bmad-build/step-04-review.md`; `docs/build/review-a-change.md`.

**Tests:**
- The I/O-matrix test audit ("a covering test that exists but did not run … counts as missing") (`step-03-implement.md`).
- The dev principles "No task complete without passing tests" and "Red, green, refactor" (`skills/bmad-agent-dev/customize.toml`).
- The verification-gap lens looks for untested behaviour changes (`skills/bmad-build/review-prompts/verification-gap.md`).

**Ticket validation:**
- Fresh-context subagents run the Ticket/Set/Tree/Dependencies/Closure checks, and findings are sorted into fix/suggest/ask (`skills/bmad-agent-po/references/validate.md`, `validate-checks.md`).
- "Spec Law" (8 rules) and Self-validate (`references/spec.md`).

**Deterministic linters:**
- `lint_spine.py`: placeholders, duplicate or non-monotonic `AD-n`, missing Binds/Prevents/Rule, unpinned stack versions (`skills/bmad-architecture/scripts/lint_spine.py`).
- `tickets.py` structure checks.
- PRD validation checklist and HTML report (`skills/bmad-prd/assets/prd-validation-checklist.md`).
- Editorial `doc_standards` lenses at finalize (`docs/customize/adopt-bmad-across-a-team.md` › Recipe 6).

**Constitution/principles:**
- There is no constitution file: absent (checked: `docs/`, `skills/`).
- The equivalents are the verified `AGENTS.md` block from `bmad-project-context` (policy, conventions, pitfalls), plus per-skill `persistent_facts` and agent `principles`.

**Definition of done:**
- Plan `built` vs `done`; the human marks `done` (`tools/ticket-tree-rules.md`).
- The epic's "Done when" checks.
- The retrospective verdict: `accepted` / `accepted-with-open-items` / `rejected`. Unfinished tickets force `rejected` (`docs/build/finish-an-epic.md`).
- Sofia's Closure check verifies "against implementation evidence, not child status" (`validate-checks.md` › Closure).

**Framework self-tests:** the repo runs `validate_skills.py --strict` and pytest for its scripts. Its stated policy: "Do not write automated tests for LLM output" (`AGENTS.md`).

## 9. Parallel, team and multi-repo

**Concurrent changes:**
- "Independent epic streams can proceed in parallel when their boundaries are explicit. Each stream needs an owner" (`docs/plan/choose-a-planning-path.md`).
- The spine is what makes parallel epics safe (`docs/plan/plan-inside-an-organization.md` › Several Epics at Once).
- Project-level parallelism "needs a higher coordination layer" (`docs/build/autonomous-development-loops.md`).
- Conflict handling between concurrent agents is not specified beyond the Dependencies "Collisions" check: "items with no dependency path share no code, config, schema, or setup; else add an `after` or merge them" (`skills/bmad-agent-po/references/validate-checks.md`).

**Worktrees:** recommended for polyrepos ("a bare clone per project, and a worktree per branch … agents working in parallel do not collide"). `bmad migrate method` asks about worktrees (`skills/bmod-method/help/monorepo-and-polyrepo.md`). The skills do not create worktrees automatically: absent (checked: `skills/bmad-build*`, `docs/`).

**Multi-repo:**
- Install at the workspace root and keep the store in its own git repo. "A ticket names the projects it touches" (`docs/plan/set-up-the-ticket-tree.md`; `skills/bmod-method/help/monorepo-and-polyrepo.md`).
- Per-initiative focus is set by `active_initiative` (personal config).

**Git, branches and PRs:**
- Build checks for a clean tree and a sensible branch, and records `baseline_revision`.
- It commits locally with a conventional message, "NEVER auto-push", and offers to create a PR (`skills/bmad-build/step-01…`, `step-05-present.md`).
- Build Auto requires a clean tree; "the branch must fit the ticket's epic"; it commits but does not push (`docs/build/autonomous-development-loops.md`).
- Sofia commits approved tree changes on the current branch and never pushes (`skills/bmad-agent-po/references/board.md`).

**Trackers:** repo store (default), or GitHub Issues, Jira, Linear, Notion or Trello. Markdown remains the working copy; tracker support is "still need[s] a lot of testing" (`docs/plan/set-up-the-ticket-tree.md` › Configure Where Tickets Are Tracked).

**Release/version handling for user projects:** absent (checked: `docs/`, `skills/bmad-build`, `tools/ticket-tree-rules.md`). `tools/release.md` covers BMad's own release only.

## 12. Setup cost and ceremony

**Install (V7):**
- Prerequisites: Node.js/npm, Git, `uv`, and a skills-capable tool.
- Steps: `npx skills add bmad-code-org/BMAD-METHOD --skill '*'` (or the plugin marketplace), then ask the `bmad` skill to run `bmad setup`, then restart the tool (`docs/start/install-bmad.md`).
- Security scanners on skills.sh flag some skills Med/High risk. Reasons: `uv run` scripts, customizable activation steps, and reading third-party text (`docs/start/install-bmad.md` › Security Scan Warnings).

**Install (stable v6.12):** `npx bmad-method install` (Node 20.12+, Python 3.10+, uv).

**Files generated:**
- Skill directories in the tool's skills folder.
- `_bmad/`: config TOMLs, `scripts/` (renderer, resolvers, memlog), `method/scripts/tickets.py`, `custom/`, and rendered snapshots under `_bmad/render/` with a `manifest.json`.
- `_bmad-output/` for documents and tickets.

Sources: `docs/start/install-bmad.md` › What You Get; `tools/ticket-tree-rules.md`; `CHANGELOG.md` v6.11.0 (snapshots).

**Minimum steps for one small change:**
1. `/bmad-build <intent>` in a fresh chat.
2. Answer any open questions and approve the plan, when the route is full.
3. Build implements, reviews, fixes and commits locally.
4. Optionally ask for a PR.

Source: `docs/build/build-a-change.md`.

**Fast paths:**
- The oneshot route: implement in-session with a minimal plan and review afterwards. The default selection rule is "100 lines or fewer: oneshot" (`skills/bmad-build/customize.toml` › `route_selection`). The docs describe the light path differently, as the absence of intent gaps, irreversible actions, and a large footprint (`docs/build/build-a-change.md` › 4).
- Users can ask for one-shot and/or skip review.
- For a trivial edit: "skip the process and ask the agent to make it directly" (`docs/build/build-a-change.md` › Size the Work).
- A story can be built from its entry without a story file (`docs/plan/set-up-the-ticket-tree.md`).

**Ceremony cost:**
- A thorough review is "slow, expensive"; the Build default is quick (`docs/build/review-a-change.md` › Choose the Depth).
- The docs justify the cost: "Ten seconds of your attention costs more than ten minutes of inference".

## 13. Agent context efficiency

**Scoped reads:**
- Read the ticket at the right altitude in full. Its sources are already distilled, so they are not re-read. "Open a companion only when the step needs it" (`skills/bmad-agent-po/workflow.md` › Dispatch; `skills/bmad-build/step-01-clarify-and-route.md` › Ticket resolution).
- For continuity, Build reads only the prerequisite plans in the same epic.

**Size budgets:**
- Plan target 900–1600 tokens ("above 1600 risks context-rot").
- Sofia's input ceiling is "a few tens of thousands of tokens, roughly a 40-page document"; condense first.

Sources: `skills/bmad-build/workflow.md`; `docs/plan/choose-a-planning-path.md`.

**Step-file architecture:** "Just-In-Time Loading: Only load the current step file … NEVER load multiple step files simultaneously" (`skills/bmad-build/workflow.md`).

**Subagents:**
- Deep investigation goes to subagents that "return short summaries only" (`step-02-plan.md`).
- The implementer receives only the plan path.
- Reviewers receive the diff as a file path, "never pasted" (`step-04-review.md`).

**Minimal project context:** a small verified `AGENTS.md` block. "Repo overviews, directory trees, and tech-stack lists never enter … A stored copy goes stale and costs tokens on every call" (`docs/existing-codebases/theory-of-project-context.md`; `set-and-maintain-project-context.md`).

**Default loads:** `persistent_facts` ships empty, so nothing auto-loads (`CHANGELOG.md` v6.12.0 › Breaking).

**Repo policy:** "Skills … are prompt text an agent reads in full on every run. Length and ambiguity are paid on every run" (`AGENTS.md`).

**Sharding:** document sharding (v4 `prdSharded`, `devLoadAlwaysFiles`) is gone. `bmad-shard-doc` and `bmad-index-docs` were removed in v6.11 (`V4:bmad-core/core-config.yaml`; `CHANGELOG.md` v6.11.0 › Removed). Brownfield guidance keeps the greenfield PRD out of reach of ordinary changes (`docs/existing-codebases/start-in-an-existing-codebase.md`).

**Token cost signals:** qualitative only. Quick review is "several times cheaper" than thorough. There is no token metering: absent (checked: `docs/build/review-a-change.md`, `skills/`).

## 14. Known limitations

**Documented limitations:**
- V7 is a preview alpha: "Expect breaking changes between updates" (`README.md`; `docs/start/install-bmad.md` caution box).
- Trackers: "The tracker options still need a lot of testing … Hooks are not integrated yet, so nothing syncs on its own" (`docs/plan/set-up-the-ticket-tree.md`).
- Subagents:
  - Build Auto halts `blocked` with `no subagents` if none are available (`docs/build/autonomous-development-loops.md`).
  - When vendors change subagent behaviour, lenses run serially or in the main session, "far worse for review quality" (`docs/build/review-a-change.md` › Your platform).
  - Without subagents, Build asks the human to run reviewer prompts in other sessions (`step-04-review.md`).
- `bmad-loop` "does not dispatch from the ticket tree yet" (`docs/build/autonomous-development-loops.md`).
- Sofia "silently loses the parts that mattered" when input exceeds the context ceiling (`docs/plan/choose-a-planning-path.md`).
- No-plan review "cannot tell a deliberate choice from a mistake" (`docs/build/review-a-change.md`).
- `bmad-qa-generate-e2e-tests` "covers the main path and the errors a user can see, and no more" (`docs/build/test-completed-work.md` › Limits).
- `uv` is a hard requirement. Rendered skills halt without it (`CHANGELOG.md` v6.11.0).
- Translated docs and web bundles were removed (`CHANGELOG.md` Unreleased › Breaking).
- Docs inconsistency in the preview: `docs/customize/add-modules.md` still tells users to run `npx bmad-method install` (the v6 installer), while the install page says that path does not apply to V7.

**Open-issue themes** (https://github.com/bmad-code-org/BMAD-METHOD/issues, page 1, fetched 2026-10-19; 53 open):
- `tickets.py` state integrity:
  - #3111 `mark` rewrites the first `status:` line while readers take the last.
  - #3112 a partial write truncates a plan.
  - #3058 loose plans are reported as problems.
- Gate bypass: #3040 "A build started on a named ticket skips the gates tickets.py next applies".
- Traceability: #3063 `baseline_revision` does not survive a squash merge.
- Review reliability:
  - #3066 the verification-gap layer reports clean when it cannot read the content.
  - #3042 request for a static-analysis/vulnerability lens.
  - #3092 trust boundaries only at code review.
- Offline: #3114 rendered skills cannot render offline (`uv run --no-cache` refetches jinja2).
- Planning-skill bugs (v6.12): #3044, #3051–#3054. Epic closure: #3046, #3070.
- Windows line endings in memlog: #3081.

**FAQ caveats:** "Why does this take so long?" and "Why does review take forever?" (`docs/build/build-a-change.md`, `docs/build/review-a-change.md`). Too many `AGENTS.md` rules or huge files can blow the reviewer context.

## 15. Assessment (opinion)

**Strengths**
1. **The review-and-triage pipeline is the most developed part.** Parallel independent lenses, mandatory per-finding verification, and a logged verdict for every finding. Routing to intent-gap, bad-plan, patch or defer re-derives code from a fixed plan instead of patching diffs. There is a bounded loop limit. (§8; `skills/bmad-build/step-04-review.md`)
2. **Clear write ownership and derivation.** One skill writes each document. Requirements are re-derived from an append-only memlog with stable `R<n>` ids. PRD `FR` → `R` → `covers` → plan → baseline commit gives a concrete forward trace, checked by validation subagents. (§3, §5)
3. **Right-sizing without named tracks.** Light vs full route inside one Build. Stories can be built from a one-line entry. Explicit advice to skip BMad for trivial edits. This replaced the earlier Level/track system. (§2, §12)
4. **Deliberate context discipline.** Plan token budgets, JIT step files, subagent summaries, a "minimal verified AGENTS.md" stance backed by a stated theory, and no auto-loaded facts. (§13)
5. **Usable with an existing organisation.** Five named sign-off moments, tracker publishing, MCP-based handoffs to Confluence and Jira, and layered team/personal overrides without forking skills. (§2, §9, §11)
6. **Deterministic tooling where it matters.** `tickets.py` (about 1.9k lines with about 2k lines of tests), `lint_spine.py`, the content-addressed render snapshots. (§6, §8)

**Weaknesses**
1. **Unstable surface right now.** The default branch is a breaking alpha past its ETA. Stable v6.12 has a different artifact model (`sprint-status.yaml`, `planning_artifacts`), and migration is required. The docs mix the two (`add-modules.md`). (§0, §14)
2. **No living system spec of delivered behaviour.** Changes are expressed as new tickets and plans. Reconciling built code back into the PRD or spec is manual ("apply … by hand"). There is no delta/merge model, so "current truth" for brownfield work is mainly the code plus a small `AGENTS.md` block. (§4)
3. **Impact analysis is mostly LLM judgment.** Only structural tree checks and ID-citation staleness are mechanical. There is no code-to-requirement dependency tracking, and code → reason relies on commit ranges that a squash merge breaks (#3063). (§5, §6)
4. **Heavy dependence on host features.** Subagents are required for quality review and for Build Auto. `uv` and network access are needed for rendering (#3114). Review quality degrades with vendor changes. (§14)
5. **Parallelism and multi-repo are guidance, not mechanism.** Worktrees are recommended but not created. Conflict handling is a validation check. The orchestrator (`bmad-loop`) cannot yet read the tree, and there is no release/version handling for the user's product. (§9)
6. **No human dashboard of its own.** The board is chat plus files or an external tracker that does not sync automatically. Visual output is limited to per-run HTML keepsakes and reports. (§10)
